# Assurance: инвариант «нет тихой потери»

Цель проекта — не «совпало на одной конфигурации», а уверенность, что любая
конфигурация либо воспроизводится полностью, либо честно отвергается. Этот
документ фиксирует инвариант, измерители и текущее состояние.

## Инвариант

Экспорт объекта обязан быть **тотальным**:

1. каждое поле/слот записи либо отнесено к свойству, либо явно
   классифицировано как padding/неизвестное;
2. осталось неразобранное — это **ошибка**, а не пропуск;
3. собранный XML содержит только элементы и атрибуты, объявленные в XDTO;
4. `parse(emit(x)) == x` для каждого объекта.

Следствие: «молча неправильно» исключено. Либо байт-в-байт, либо отказ с
указанием места.

## Переключатели

| Переключатель | Что делает |
|---|---|
| `IBCMD_RS_FAIL_ON_MODEL_FALLBACK=1` | строка, которую модель не может записать, **валит экспорт** вместо передачи legacy-конвертеру |
| `IBCMD_RS_MODEL_EXPORT_SHADOW=1` | legacy-конвертер прогоняется на тех же строках, байты сравниваются |
| `--fail-on-opaque` (cf export) | падение, если остались непрозрачные storage-записи |

Первый переключатель — fail-closed сторона инварианта для модельного слоя.
Второй — оракул: он сравнивает наш вывод с независимой реализацией на каждой
строке, а не на выборочных файлах.

## Базовый замер (ServiceDesk 3.10.28, платформа 8.5.1.1529)

Экспорт без fail-closed: 1961 строка, код 0, побайтово совпало 1954.

Fallback'и модели — **1 строка** (единственные места, где модель уступает
legacy-конвертеру):

| Строка | Причина |
|---|---|
| `9565660f-9e2b-48f4-8b45-6dd6bbfa04c2` | `ExternalDataSource requires the exact empty child collections` — модель умеет только пустой внешний источник |

С `IBCMD_RS_FAIL_ON_MODEL_FALLBACK=1` тот же экспорт завершается кодом −1, и
**одна ошибка перечисляет все строки**, а не первую:

```
[ERROR] model export fell back on 1 row(s) with fail-closed enabled:
[ERROR]   9565660f-…: ExternalDataSource requires the exact empty child collections
```

Это и есть работающий инвариант: дырка не прячется за успешным деревом, и
карта покрытия собирается за один прогон.

## Ворота импорта: первый факт

Правильная команда загрузки XML — не `config import` + `config apply`, а
`infobase create --import=<dir> --apply` (см. `ibcmd-help-infobase.txt`).
Но и она на нативной выгрузке ServiceDesk завершается отказом:

```
[INFO] Импорт конфигурации из XML успешно завершен
[INFO] Проверка корректности метаданных...
Нарушена целостность структуры конфигурации.
```

Это происходит и с **неизменённой** выгрузкой, то есть дело не в правке
отдельного файла, а в самом маршруте XML→база для этого экспорта.

Матрица экспериментов (все — платформа 8.5.1.1529, пустая база MSSQL):

| Сценарий | Импорт | Apply |
|---|---|---|
| пустая база → XML → пустая база | ок | **ок** |
| ServiceDesk, как есть | ок | отказ |
| без `ConfigDumpInfo.xml` | ок | отказ |
| без каталога `Ext` | ок | отказ |
| uuid языка «Русский» = uuid пустой базы | ок | отказ |
| `.cf` через `infobase create --load` | — | **ок** |
| OneConta85 (другая реальная конфигурация), как есть | ок | отказ |
| листовые виды (боты, HTTP, XDTO, задания, подписки) убраны | ок | отказ |
| роли убраны | ок | отказ |

Ключевой факт: **другая реальная конфигурация ведёт себя так же**. Значит
проблема не в ServiceDesk и не в отдельных видах объектов, а в самом
маршруте XML→база: платформа применяет XML пустого конфига и отказывает
любому содержательному.

Следствия:

- ворота «импорт принимается платформой» в этой среде проходят только через
  `.cf` (`infobase create --load`);
- XML-маршрут остаётся для сравнения выгрузок и для проверки отдельных
  объектов, но не как ворота импорта;
- бисект по видам дальше вести не имеет смысла, пока не понято, чем XML
  пустого конфига отличается от содержательного (вероятно, служебные
  идентификаторы корня, которые платформа не переносит);
- сравнивать состояние БД до этого бессмысленно.

## Как закрываются дырки

1. **Факт, а не пример.** Каждое правило выводится из ресурса платформы
   (XDTO/`*_root.res`) или декомпилированного диспетчера (REA), а не из одного
   объекта.
2. **Схема, а не имя.** В коде не должно быть веток по именам объектов
   конфигурации.
3. **Обе стороны.** Тест проверяет и наличие элемента, и его отсутствие.
4. **Матрица.** Правило принимается, только если не ломает другие
   конфигурации (регрессия), а не только ту, где дефект найден.
